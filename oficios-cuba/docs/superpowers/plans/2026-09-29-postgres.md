# Plan 1 — Postgres + PostGIS en lugar de SQLite

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** La aplicación hace exactamente lo que hace hoy, pero sobre Postgres 18 + PostGIS, con búsqueda por `tsvector` en vez de `LIKE '%x%'`, y la suite entera en verde.

**Architecture:** Un servicio `oficio_db` nuevo en la red interna `oficio_net`. El esquema nace limpio en la v1 (no se portan las 13 migraciones de SQLite, porque no hay datos que conservar). Una capa de datos `q`/`qOne`/`tx` sobre `pg` reemplaza `better-sqlite3`, y las 293 consultas síncronas pasan a asíncronas dominio por dominio. Meilisearch **no entra en este plan**: aquí el `tsvector` es la búsqueda, y en el Plan 2 pasa a ser el respaldo.

**Tech Stack:** Postgres 18 + PostGIS 3.6 (`postgis/postgis:18-3.6`, Debian), `pg` con Pool, Node 22, Express 4, vitest + supertest.

**Spec:** `docs/superpowers/specs/2026-09-29-postgres-meilisearch-design.md`

## Global Constraints

Estas reglas aplican a **todas** las tareas. Los requisitos de cada tarea las incluyen implícitamente.

- **Imagen de base de datos:** `postgis/postgis:18-3.6` exactamente. Debian, **no** `-alpine`: hace falta ICU completo para colación y acentos en español.
- **Driver:** `pg` (node-postgres) con `Pool`. No `postgres.js`, no `pg-native`.
- **Marcadores de posición:** `$1, $2, …` en vez de `?`. Nunca interpolar valores en el SQL.
- **Ninguna consulta dentro de `tx()` puede usar el pool.** Solo el cliente que `tx()` entrega. Una consulta que use el pool dentro de una transacción se ejecuta fuera de ella sin dar error, y corrompe datos en silencio.
- **Red y puertos:** `oficio_db` va solo en `oficio_net`, **sin** `ports:`, sin entrar en `net_dmz` y sin labels de Traefik. La superficie de ataque externa no cambia.
- **Secretos:** `POSTGRES_PASSWORD` va en `.env` con `chmod 600`, nunca en `docker-compose.yml`. El plan crea la clave vacía; Dariel pega el valor.
- **`'premium'` no existe.** Ni en el esquema, ni en los `CHECK`, ni en `PLAN_WEIGHT_SQL`, ni en `CON_NEGOCIO_SQL`, ni en `CON_CATALOGO_SQL`. Los planes son `free`, `basic`, `pro`.
- **`lib/ubicacion.ts` no se toca.** El desplazamiento de 100–300 m lo sigue calculando `desplazar()` en JS con `node:crypto`. PostGIS indexa el resultado; no lo genera.
- **El filtro del mapa usa solo la coordenada pública**, nunca `pp.lat`/`pp.lng`. Filtrar por la exacta reabre el oráculo de bisección.
- **Idioma:** todo el texto de la UI y los mensajes de error en español de Cuba, con tuteo. Commits en español.
- **Durante el porte la suite está roja.** Cada tarea de porte deja en verde **su propio archivo de test**; "toda la suite en verde" es el criterio de la última tarea. Es una propiedad de cambiar el motor de base de datos, no un defecto del plan.

## Review Focus

Cinco formas en que este porte rompe cosas que la spec da por hechas. Cada línea tiene su test asignado a la tarea que posee el código.

1. **Un id inválido en la URL deja de dar 404 y pasa a dar 500.** Hoy `GET /api/providers/abc` devuelve 404 porque los ids son `TEXT`. Con columnas `uuid`, Postgres lanza el error de sintaxis `22P02` y el `errorHandler` lo convierte en 500. Cualquiera que teclee mal un enlace lo ve. → Tarea 6.
2. **`pg` devuelve `jsonb` ya parseado, no una cadena.** Los 19 `JSON.parse(...)` del código reventarán con "not valid JSON" al recibir un objeto. Afecta a fotos de servicios, lista de precios, galería, agenda y `notify_prefs`. → Tarea 5.
3. **`pg` devuelve `timestamptz` como objeto `Date`, no como cadena ISO.** Toda respuesta que hoy manda una fecha como texto cambia de forma, y el frontend y las dos apps muestran "Invalid Date". → Tarea 5.
4. **Los booleanos pasan de `0`/`1` a `true`/`false`.** Donde el valor sale crudo al JSON, el contrato cambia para las apps móviles. → Tarea 5.
5. **`LIKE` es sensible a mayúsculas en Postgres y no en SQLite.** Cualquier `LIKE` que sobreviva al porte hará que buscar "ARROZ" no encuentre "arroz". → Tarea 14.

```typescript
import type { PoolClient } from 'pg';
import { pool } from './conexion.js';

/**
 * El único modo de consultar dentro de una transacción. `tx()` entrega uno de
 * estos y no el pool a propósito: una consulta que use el pool dentro de una
 * transacción se ejecuta FUERA de ella y sobrevive al rollback, sin dar ningún
 * error. El test 'lo que se escribe con el pool dentro de una transacción NO se
 * deshace' documenta ese fallo.
 */
export type Tx = {
  q<T>(sql: string, params?: unknown[]): Promise<T[]>;
  qOne<T>(sql: string, params?: unknown[]): Promise<T | undefined>;
};

export async function q<T>(sql: string, params: unknown[] = []): Promise<T[]> {
  const { rows } = await pool.query(sql, params);
  return rows as T[];
}

export async function qOne<T>(sql: string, params: unknown[] = []): Promise<T | undefined> {
  const { rows } = await pool.query(sql, params);
  return rows[0] as T | undefined;
}

export async function tx<T>(fn: (c: Tx) => Promise<T>): Promise<T> {
  const cliente: PoolClient = await pool.connect();
  const dentro: Tx = {
    async q<R>(sql: string, params: unknown[] = []) {
      const { rows } = await cliente.query(sql, params);
      return rows as R[];
    },
    async qOne<R>(sql: string, params: unknown[] = []) {
      const { rows } = await cliente.query(sql, params);
      return rows[0] as R | undefined;
    },
  };
  try {
    await cliente.query('BEGIN');
    const valor = await fn(dentro);
    await cliente.query('COMMIT');
    return valor;
  } catch (e) {
    await cliente.query('ROLLBACK').catch(() => {});
    throw e;
  } finally {
    cliente.release();
  }
}
```

```typescript
import { readFileSync } from 'fs';
import { resolve } from 'path';
import { q, tx } from './acceso.js';

export const ESQUEMA_VERSION = 1;

/**
 * Aplica el esquema si la base está vacía. No hay migraciones incrementales
 * todavía: el esquema nació limpio en la v1 de Postgres, sin arrastrar las 13
 * migraciones de la época de SQLite. Cuando haya que cambiar el esquema con
 * datos reales en producción, esta función crece con un array de migraciones
 * como el que tenía db/index.ts.
 */
export async function migrar() {
  await q(`CREATE TABLE IF NOT EXISTS schema_migrations (
    version integer PRIMARY KEY,
    applied_at timestamptz NOT NULL DEFAULT now()
  )`);

  const ya = await q<{ version: number }>('SELECT version FROM schema_migrations');
  if (ya.some((r) => r.version === ESQUEMA_VERSION)) return;

  const sql = readFileSync(resolve(__dirname, 'esquema.sql'), 'utf8');
  await tx(async (c) => {
    await c.q(sql);
    await c.q('INSERT INTO schema_migrations (version) VALUES ($1)', [ESQUEMA_VERSION]);
  });
}
```

```typescript
 * distinto — el defecto que obligaba a repetir el filtro en tres archivos.
 *
 * En el Plan 2 este módulo gana un adaptador de Meilisearch y esta
 * implementación pasa a ser el respaldo.
 */
export function termino(
  bruto: string | undefined,
  columna: string,
  siguienteParam: number,
): { sql: string; params: unknown[] } | null {
  const limpio = (bruto ?? '').trim();
  if (!limpio) return null;
  // websearch_to_tsquery no lanza con comillas o operadores sueltos, al
  // contrario que to_tsquery: el usuario puede escribir lo que quiera.
  return {
    sql: `${columna} @@ websearch_to_tsquery('spanish', unaccent($${siguienteParam}))`,
    params: [limpio],
  };
}
```

Se usa así, en la ruta (ejemplo de `catalog.ts`):

```typescript
const t = termino(q, 'ci.busca', params.length + 1);
if (t) { where += ` AND ${t.sql}`; params.push(...t.params); }
```
